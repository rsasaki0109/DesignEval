# DesignEval 評価レポート

## 1. 問題の整理

- 長いURLを短い一意のコードに変換するサービスの設計
- 短縮URLからのリダイレクト（読み取り重視: 100:1）
- クリック統計の追跡機能
- カスタム短縮URL対応
- 有効期限管理
- 月間1億URL作成、10年保持という大規模要件

## 2. 設計内容の抽出

### 目的

TinyURL/bit.ly相当のURL短縮サービスの設計。大規模トラフィックに対応し、統計機能も持つ。

### 前提・仮定

書き込み約40 URL/秒、読み取り約4,000リクエスト/秒と定量的に算出。10年で120億URLのストレージ見積もり。

### コンポーネント構成

API Layer (Nginx LB + stateless App Servers)、PostgreSQL、Redis Cache、Snowflake風ID生成サービス、Kafka + 集計DB（統計用）

### データフロー

書き込み: Client → LB → App → ID生成 → Base62 → PostgreSQL + Redis。読み取り: Client → LB → App → Redis (hit) or PostgreSQL (miss) → リダイレクト + Kafkaへ非同期イベント送信。

### 状態管理

PostgreSQLが正のデータソース。Redisはキャッシュ層（TTL付き）。統計は非同期で別DBに集計。

### スケーリング戦略

App Serverの水平スケール、PostgreSQL Read Replica、Redis Cluster、将来的にshort_code先頭文字でのシャーディング。

### 障害対応

Redis障害→DBフォールバック、DB障害→Read Replicaフェイルオーバー、ID生成障害→ローカルIDバッファ。

### 監視・運用

明示されていない

## 4. 良かった点

- 定量的な見積もり（QPS、ストレージ）から設計を導出している
- Base62エンコードの計算（62^7≈3.5兆）で十分性を証明
- カウンター vs ハッシュ方式のトレードオフを具体的に議論
- 301 vs 302リダイレクトの選択理由が明確
- 統計をKafkaで非同期分離する設計が実務的
- ID生成障害時のローカルバッファという具体的な対策

## 5. 弱い点・不足点

- セキュリティの考慮が完全に欠落（悪意あるURL、フィッシング対策、レート制限）
- 監視・ログ・アラートへの言及がゼロ
- 有効期限付きURLの削除・クリーンアップ戦略が未記載
- カスタムURL機能のフロー詳細が不足
- データのバックアップ・復旧戦略が未記載
- URLの検証（有効なURL形式か、到達可能か）への言及なし

## 6. トレードオフ分析

### レイテンシ vs コスト

Redisキャッシュでレイテンシを下げるが、インフラコストが増加する。キャッシュヒット率80%の仮定は妥当だが、根拠が示されていない。

### 一貫性 vs 可用性

Read Replicaによるeventual consistencyを許容。問題要件に沿った判断。新規URLがReplicaに伝播するまでの遅延は実用上問題ない。

### シンプルさ vs 拡張性

Kafkaの導入はMVPとしてはやや複雑だが、統計機能の拡張性を確保する妥当な判断。

### 集中型 vs 分散型

ID生成を分散サービスとして設計し、SPOFを回避。ローカルバッファによる障害対応も具体的。

## 8. 改善提案

### 改善1: セキュリティレイヤーの追加

- **理由**: 短縮URLはフィッシングやマルウェア配布に悪用されやすい
- **軽減するリスク**: ブランド毀損、ユーザー被害、サービス停止

### 改善2: 監視・オブザーバビリティの設計

- **理由**: 運用なしにはサービスを維持できない。障害検知、キャパシティプランニングに必須
- **軽減するリスク**: サイレント障害、パフォーマンス劣化の見逃し

### 改善3: 有効期限クリーンアップの設計

- **理由**: 10年間のデータ蓄積により、未処理だとストレージが無限増加する
- **軽減するリスク**: ストレージコスト増大、クエリ性能劣化

### 改善4: レート制限の導入

- **理由**: API濫用・DoS攻撃からの保護が必要
- **軽減するリスク**: サービス過負荷、リソース枯渇

### 改善5: カスタムURLのフロー詳細化

- **理由**: 要件にあるが設計が薄い。予約語、衝突、バリデーションルールの明確化が必要
- **軽減するリスク**: 実装時の曖昧さ、不正なカスタムURL
